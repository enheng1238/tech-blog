# NumPy 2.5 发布：告别 distutils，拥抱自由线程时代

## 引言：Python 数据科学的基石迎来新版本

2026 年 7 月 4 日，NumPy 发布 **2.5.1** 补丁版本，这是当前最新稳定版（2.5.0 于 6 月 21 日发布）。作为 Python 数据科学生态的基石，NumPy 的每次大版本更新都会影响下游数以万计的库与项目。2.5 系列的发布说明中反复出现三个关键词：**过渡（transitional）**、**free-threading（自由线程）**、**Python 3.15**——这三个词串起了 NumPy 2026 年的演进主线。

## 一、过渡版本：distutils 时代正式落幕

NumPy 2.5.0 被官方定义为“过渡版本”（transitional release），其最引人注目的动作是：**彻底移除 distutils，并终止对 Python 3.11 的支持**。

distutils 是 Python 标准库中历史悠久的构建工具，NumPy 长期依赖它作为构建系统的一部分。随着 Python 生态全面转向 setuptools 与 Meson 等现代构建方案，distutils 的移除是顺理成章的结局。这意味着：如果你的项目还在以任何方式依赖 distutils 相关的 NumPy 内部接口，升级到 2.5 前必须完成迁移。

同时，2.5.0 大量到期了 2.0.x 时代引入的 deprecation（弃用警告）。NumPy 遵循“先警告、后移除”的渐进策略：2.0 系列开始标记废弃的 API，经过若干版本过渡，在 2.5 中正式删除。这种节奏保证了生态有足够时间迁移，但也意味着——**升级到 2.5 时，请务必检查代码中是否存在旧版 deprecation 警告**，它们很可能已经在 2.5 中被移除。

## 二、free-threading：为 Python 无 GIL 时代铺路

如果说 distutils 移除是“告别过去”，那么 free-threading 支持则是“拥抱未来”。

Python 3.13 引入了实验性的自由线程模式（free-threaded build，即不带 GIL 的 Python），让多线程程序可以真正并行执行 Python 代码。作为 Python 数值计算的核心，NumPy 必须为此做好准备。2.5.0 在这方面有多项底层优化：

- **无锁 ufunc 分发表**：ufunc（通用函数，如 `np.add`、`np.dot`）的分发表改为无锁实现，减少了多线程下的锁竞争；
- **不可变共享对象**：全局内存对象（如单例）转为不可变，避免多线程并发访问时的数据竞争；
- **优化内存分配**：改用 `PyMem_RawMalloc` 等原始分配接口，降低多线程内存分配的开销。

这些优化对普通用户来说是透明的——你的代码不用改，但在 free-threaded Python 下运行时会获得更好的并发性能。对于正在构建多线程数据管线的开发者，这意味着“Python 多线程算不动”的痛点正在被逐步解决。

## 三、新特性：降序排序与 DLPack 扩展

2.5.0 还带来了两个值得关注的新能力：

**降序排序（descending sorts）。** NumPy 的排序函数此前只支持升序，降序需要 `np.sort(arr)[::-1]` 这类技巧。2.5.0 让排序与 Array API 标准对齐，支持原生降序排序。虽然改动不大，但对代码可读性是一处实在的改善，也体现了 NumPy 持续推进 Array API 标准化的决心：

```python
import numpy as np

arr = np.array([3, 1, 4, 1, 5, 9, 2, 6])
# 2.5 之前：降序需要反转技巧
desc_old = np.sort(arr)[::-1]
# 2.5 之后：直接指定降序
desc_new = np.sort(arr, descending=True)
```

**DLPack 用户自定义 dtype。** DLPack 是跨框架的张量交换标准（PyTorch、JAX、CuPy 等均支持）。2.5.0 允许为用户自定义的 dtype 注册 DLPack 导入导出，这意味着自定义数据类型可以更顺畅地在不同深度学习框架间传递——对生态互操作是一大利好。

## 四、free-threading 与 GIL：为什么这对 AI 开发者很重要

要理解 free-threading 的意义，需要先回顾 GIL（全局解释器锁）的历史。CPython 的 GIL 保证同一时刻只有一个线程执行 Python 字节码，这让解释器实现变简单，但也让多线程无法利用多核 CPU 并行执行纯 Python 代码。长期以来，Python 开发者的“并行”解决方案是 multiprocessing（多进程）或把重计算下沉到 C 扩展——NumPy 的底层运算正是如此，所以单个 ufunc 本身可以并行，但多个线程同时调用 ufunc 时会受 GIL 串行化。

Python 3.13 推出的 free-threaded build 移除了 GIL，让 Python 线程可以真正并行。但移除 GIL 不等于万事大吉：所有 C 扩展都必须自己保证线程安全，否则会出现数据竞争与崩溃。NumPy 2.5 的“无锁 ufunc 分发表、不可变共享对象、PyMem_RawMalloc 内存分配”三项优化，正是为这一目标做的底层功课。

对 AI 开发者来说，这意味着什么？数据预处理、特征工程、批量推理调度这类 CPU 密集型管线，过去受限于 GIL 无法用多线程提速；在 free-threaded Python + NumPy 2.5 的组合下，`concurrent.futures.ThreadPoolExecutor` 就能获得真实的多核并行。无需重写代码，无需引入多进程的序列化开销——这是“免费”的性能提升。

## 五、新废弃项：开发者需要关注的迁移清单

2.5.0 同时引入了一批新的弃用警告，升级后可能需要调整代码：

| 废弃项 | 替代方案 |
| --- | --- |
| `numpy.char.chararray` 及 `numpy.char.[as]array` | 使用带字符串/字节 dtype 的普通 ndarray |
| 直接设置数组的 `shape` 属性 | 使用 `np.reshape`（可加 `copy=False` 避免复制） |
| 直接设置数组的 `dtype` 属性 | 使用 `array.view(dtype=new_dtype)` 创建视图 |
| 原地调整数组大小（resize） | 使用 `np.resize` 创建新数组 |
| `numpy.fix` | 使用 `numpy.trunc`（更快且符合 Array API） |
| `timedelta64` 的通用单位 | 显式指定单位，如 `'s'`（秒）或 `'D'`（天） |

这批废弃的共同逻辑是：**直接修改数组的元数据属性（shape/dtype）在多线程共享场景下不安全**，官方鼓励用返回新视图/新数组的方式替代。这与 free-threading 的导向一脉相承——让数组操作更安全、更可预期。

## 六、Python 3.15 准备与支持矩阵

2.5.1 的发布说明明确提到“Preparation for Python 3.15 continues”，并披露了 GCC 最低编译版本从 9.3.0 提升到 10.3.0。当前版本支持 **Python 3.12-3.14**；Python 3.15 将从首个 rc 版本开始获得支持。对于仍停留在 Python 3.11 及以下版本的项目，升级 Python 版本是使用 NumPy 2.5 的前提。

## 七、回顾：从 2.0 到 2.5 的迁移主线

理解 2.5 的最佳视角，是回看整个 2.x 系列的演进。2024 年发布的 NumPy 2.0 是一次“破坏性大版本”：修改了字符串表示、改变了部分类型提升规则、引入 NEP 兼容性策略，并启动了大量废弃项的倒计时。2.1 到 2.4 则是稳步修复与功能迭代期。到了 2.5，当年 2.0 埋下的废弃项集中到期——这正是“过渡版本”称谓的由来：它不是简单的新功能集合，而是一次蓄谋已久的清理。

这种“大版本立规则、小版本做过渡、后续版本清旧账”的节奏，与 Python 自身的演进哲学高度一致。对生态维护者而言，好消息是 NumPy 的每个废弃项都提供了明确的替代方案；坏消息是，如果跳过 2.1-2.4 直接从 2.0 升级到 2.5，一次性面对的变化会相当可观。建议逐版本渐进升级，每步都跑通测试套件。

## 小结与升级建议

NumPy 2.5 是一个典型的“承上启下”版本：向上兼容性上，它移除了多年沉积的旧接口；向下兼容性上，它积极拥抱自由线程与 Python 3.15。对开发者的三点建议：

1. **升级前扫描 deprecation 警告**：运行测试时开启 `-W error::DeprecationWarning`，尽早发现将在 2.5 失效的 API；
2. **关注 shape/dtype 修改方式**：如果代码中有 `arr.shape = ...` 或 `arr.dtype = ...` 这类写法，迁移到 view/reshape 方案；
3. **尝试 free-threaded Python**：如果业务有大量 CPU 密集型并行计算，值得在 free-threaded Python 3.13/3.14 上做一次基准测试，NumPy 2.5 的优化很可能带来惊喜。

作为拥有 3.2 万+ stars、1.2 万+ forks 的开源项目，NumPy 的每一步演进都牵动着整个 Python 科学计算生态。2.5 系列既是一次扎实的清理，也是一次面向未来的布局——**告别 distutils，拥抱自由线程**，这八个字正是 NumPy 2026 的主旋律。
